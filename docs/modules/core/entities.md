# Core: сущности

`core` предоставляет базовые данные сайта. Создавайте их через административный интерфейс или management API; операции требуют соответствующих прав. Ресурсные записи используют версию, поэтому для последующих обновлений передавайте полученную от API ожидаемую версию.

| Сущность | Для чего нужна и как работать |
| --- | --- |
| **Сайт (`Site`)** | Обязательное название, уникальный домен, locale, код профиля, публичность и настройки. Название служит основной подписью в админке; домен определяет адрес сайта. |
| **Ресурс (`Resource`)** | Узел сайта: страница, ссылка или библиотека. Содержит заголовок, slug/path, публикацию, меню, поля, виджеты и ссылки на медиа. Обычно сначала создают ресурс, затем добавляют widgets и настраивают публикацию. |
| **LibraryItem** | Запись большой коллекции, принадлежащей ресурсу `library`. Создаётся и редактируется через API библиотеки; имеет поля, виджеты и публикацию. URL задаётся шаблоном item URL библиотеки. |
| **Тип ресурса** | Описывает возможности ресурса. Встроенные коды: `page`, `link`, `resource_link`, `library`, `library_mirror`. `page` поддерживает шаблон, HTML-содержимое, поля и виджеты; `link` хранит внешний URL; `resource_link` указывает на другой ресурс; `library` владеет LibraryItems; `library_mirror` показывает ресурсы библиотеки-источника на текущем сайте без копирования. |
| **Шаблон** | Связывает ресурс с разметкой, полями, областями виджетов и доступными редакторами. Код шаблона указывается в ресурсе, если выбранный тип его поддерживает. |
| **Файл и папка** | Файлы расположены на filesystem-диске; папки образуют дерево. Загруженные файлы можно ссылать из полей и контента. Перед удалением API проверяет использование файла. |
| **Медиа** | CMS-представление файла с заголовком и параметрами обработки изображения. Media ID можно использовать в ресурсах и media-полях. |
| **Пользователь, группа и доступ** | Пользователи входят в группы; группам назначаются права и правила доступа к сайтам. Проверки доступа выполняются на сервисных операциях. |
| **Виджет и привязка** | Привязка виджета к ресурсу задаёт код виджета, область, вид, параметры, порядок и состояние. См. [каталог виджетов](widgets.md). |

Пример создания HTML-страницы (management-маршрут Core):

```http
POST /api/sites/12/resources
Content-Type: application/json

{"type":"page","title":"О проекте","slug":"about","content_type":"html","content":"<p>Описание проекта</p>","fields":{},"type_settings":{}}
```

`fields` и `type_settings` нужны даже при отсутствии дополнительных значений. Публикацию и включение в меню задайте последующим обновлением. API вернёт ID и версию ресурса.

## Зеркало библиотеки

`library_mirror` — самостоятельный узел дерева с собственными шаблоном, полями,
контентом, виджетами и SEO. Единственная настройка типа — положительный
`type_settings.source_library_id`. Источником может быть только `library`, в том
числе с другого сайта и другого профиля. На одном сайте разрешено одно зеркало
каждой библиотеки, включая мягко удалённые зеркала. Источник можно заменить.

Зеркалируются только `LibraryItem`; обычные дочерние узлы дерева не переносятся.
ID и владельцы ресурсов не меняются. Редактирование, ревизии и удаление ресурсов
выполняются на сайте-источнике. В админке зеркало показывает опубликованные
ресурсы источника только для чтения.

Путь ресурса складывается из пути зеркала и текущего `item_url_pattern` источника.
Изменения источника доступны при следующем чтении. Для публичной выдачи должны
быть опубликованы оба сайта, библиотека, зеркало и сам ресурс; учитываются даты
публикации, снятия с публикации и мягкое удаление.

Страница зеркала работает в runtime принимающего сайта. Страница ресурса
использует данные, шаблон, поля, виджеты и расширения runtime источника, даже если
в принимающем профиле их нет. Публичный `resource.path` содержит локальный путь.
SEO, в том числе `canonical`, вычисляется для исходного сайта и исходного пути.
Сохранённые HTML и произвольный JSON виджетов не переписываются.

Пока существует зеркало, окончательное удаление источника (включая удаление его
предка) и сайта-источника запрещено. Сначала удалите зеркало окончательно или
смените его источник. Мягкое удаление источника скрывает его ресурсы в зеркалах.

Пути проверяются в обоих направлениях: новый ресурс источника не может занять
путь обычного узла на сайте зеркала; обычный узел не может занять путь ресурса
зеркала. Проверки используют индексы маршрутов без загрузки коллекции в память.
Для потенциально пересекающихся пространств URL двух непустых библиотек действует
существующий отказ `route_mutation_requires_maintenance`: перенос или смена
шаблона URL не запускает массовую переборку записей.

Маршруты зеркальных ресурсов и результаты двух виджетов списков читаются без
долгоживущего кеша. Это позволяет учитывать изменения источника и границы
публикации без копий коллекции и массовой инвалидации принимающих сайтов.
