# Счётчик просмотров

Core считает успешные GET к `/api/resources/resolve` и его вложенным путям.
Засчитывается опубликованный ресурс после ответа 2xx. HEAD, preview, ошибки,
перенаправления, списки, меню, виджеты и поиск просмотров не добавляют. Повторный
заход считается новым просмотром; ограничений по IP нет.

Обычный GET без специальных заголовков считается навигацией. Запросы с известными
bot/crawler/spider User-Agent и `prefetch`, `prerender`, `preview` в `Purpose`,
`Sec-Purpose`, `X-Purpose`, `X-Moz`, `Sec-Fetch-Purpose` исключаются. Эти эвристики
не позволяют отличить скрытую автоматизацию, отправляющую обычные заголовки
браузера, от пользователя. Клиент предварительной загрузки должен сохранять
соответствующие заголовки.

## Подключение

Физический накопитель объявляет приложение; профиль выбирает его код. Контракт
`resourceviews.Accumulator` отдельный от `cache.Store`. Бизнес-логика и worker
зависят только от него и `resourceviews.Repository`, поэтому другой backend
можно подключить собственным `resourceviews.Factory`.

Для Redis factory использует общий `connectors/redis` и его `ClientConfig`.
Приложению не нужно импортировать `github.com/redis/go-redis/v9`: библиотека
клиента остаётся внутри connector. Redis-кэш и накопитель просмотров используют
один механизм подключения, но сохраняют отдельные контракты и настройки.

```go
import (
    "time"

    "github.com/vernal96/go-cms-kernel/app"
    redisconn "github.com/vernal96/go-cms-kernel/connectors/redis"
    "github.com/vernal96/go-cms-kernel/modules/core"
    "github.com/vernal96/go-cms-kernel/modules/core/resourceviews"
    viewsredis "github.com/vernal96/go-cms-kernel/modules/core/resourceviews/adapters/redis"
)

// Добавить к существующему app.Definition; адреса/credentials берутся из
// конфигурации инфраструктуры приложения.
var definition = app.Definition{
    ResourceViews: []resourceviews.Definition{{
        Code: "views",
        Factory: viewsredis.Factory{
            Config: redisconn.ClientConfig{Addrs: []string{"redis-views:6379"}},
            Prefix: "my-cms:resource-views",
        },
    }},
}

// Добавить к существующему core.Config профиля.
var declaration = core.New(core.Config{
    ResourceViews: &resourceviews.Config{
        Accumulator: "views",
        FlushInterval: 45 * time.Second,
    },
})
```

Если `ResourceViews` в core не задан, накопление отключено. Период по умолчанию
45 секунд. Рабочие значения для приложения — 30–60 секунд; конфигурация допускает
интервал от секунды для проверки. Factory зарегистрирован приложением, клиент
лениво открывается отдельно для каждого runtime сайта. Смена runtime/остановка
приложения отменяет worker и закрывает его клиент. Кандидат runtime, который
не начал выполнять запросы или worker, сетевых соединений не открывает.

Все экземпляры, пишущие в одну PostgreSQL, должны использовать одинаковые Redis
DB и Prefix. Для другой PostgreSQL нужен отдельный Prefix. Redis Cluster keys
одного сайта находятся в одном hash slot. Накопителю нужен отдельный Redis с
AOF и `maxmemory-policy noeviction`; вытеснение статистических ключей означает
потерю ещё не сохранённых просмотров. AOF `everysec` допускает потерю последней
секунды при отказе самого Redis; гарантии процесса Go не заменяют надёжность
настройки Redis.

## Запись и восстановление

`resource_views.counts(site_id, resource_id, total)` хранит только сохранённый
итог. В `core.resources` ничего не записывается: просмотры не меняют версию,
`updated_at`, историю и кэш контента.

Increment атомарно увеличивает pending Redis hash. Worker через заданный интервал
(по умолчанию 45 секунд) забирает до 1000 идентификаторов в неизменяемый пакет
с уникальным ID и арендой 30 секунд. Накопление новых просмотров продолжается
в pending. За один период
обрабатывается максимум 10 пакетов с общим ограничением операции 10 секунд.
Только один worker владеет пакетом сайта в пределах аренды.

В одной PostgreSQL транзакции фиксируется ID в `resource_views.batches` и
выполняется массовый `INSERT ... ON CONFLICT DO UPDATE`, увеличивающий total.
После commit Redis-пакет подтверждается и удаляется. При остановке процесса
пакет остаётся в Redis, после истечения аренды другой worker забирает тот же ID.
Если предыдущий процесс успел сделать commit, повторная запись не увеличит итог.
Даже возобновившийся после долгой паузы старый worker защищён от повторной записи
ID в PostgreSQL и не может подтвердить чужую аренду.

Идентификаторы обработанных пакетов сохраняются без автоматического удаления
и без каскадного удаления при удалении исходного сайта:
это необходимо для безопасного повтора произвольно задержанного worker.
При постоянном трафике и одном пакете каждые 45 секунд — около 1920 небольших
строк на активный сайт в сутки. Удалять этот журнал по TTL без ограничения
времени жизни старых worker нельзя.

При недоступном Redis CMS продолжает возвращать публичные ответы; накопление
ограничено 250 мс и ошибка логируется как `resource_views.increment.failed`.
Просмотры за время недоступности не сохраняются. Worker логирует ошибки как
`resource_views.flush.failed`, продолжает работу и повторяет запись после
восстановления. Недоступность Redis при запуске не блокирует startup. При
недоступной PostgreSQL пакет остаётся для последующего повтора.

LibraryItem имеет тот же механизм по собственной паре site/item ID. Просмотр
элемента через зеркало увеличивает счётчик оригинального LibraryItem. Просмотр
корня зеркала увеличивает счётчик исходной библиотеки. Worker исходного сайта
может находиться на другом экземпляре CMS, поскольку pending хранится в общем
Redis. Если исходный сайт не имеет активного runtime ни на одном экземпляре,
его pending остаётся до появления worker.

Мягкое удаление прекращает новые просмотры и сохраняет итог. Окончательное
удаление каскадно удаляет итог; остаток pending для исчезнувшего идентификатора
пропускается при сохранении пакета, не блокируя другие ресурсы. Перенос ресурса
на другой сайт переносит сохранённый итог через FK `ON UPDATE CASCADE`; pending
старого сайта после переноса сохраняется под текущим сайтом того же стабильного
ID ресурса. Идентификаторы пакета приходят из доверенного накопителя ядра.

## Админка

Detail DTO ресурса возвращает `resource.views_total`, LibraryItem —
`item.views_total`, тип — integer. Это сохранённое значение PostgreSQL;
несохранённые просмотры появятся после очередного flush. Detail зеркальной
библиотеки читает итог исходной библиотеки, не требуя доступа к её редактору.
После удаления оригинала итог зеркала равен нулю. Статистика не входит в
редактируемые поля или snapshot ревизии.
