# Адреса HTTP API

Внешний префикс CMS API — `/api`. Базовый адрес локального API:
`http://localhost:8080/api`. Во всех примерах документации запросы содержат полный
путь от корня домена.

Префикс `/api` включён в kernel `v0.4.0`, закреплённый в Starter. Обычная
Docker-сборка использует эти адреса без локального Go workspace или `replace`.

| API | Внешние адреса |
| --- | --- |
| Вход и выход | `POST /api/auth/login`, `POST /api/auth/logout` |
| Админка | `/api/admin/...` |
| Сайты, ресурсы и модули управления | `/api/sites/...`, `/api/site-profiles` |
| Файловый менеджер и media | `/api/files/...`, `/api/media/...` |
| Окончательное удаление плитки | `POST /api/sites/{siteID}/media/{mediaID}/delete-file`, `GET /api/sites/{siteID}/media-file-deletions/{operationID}` |
| Системное администрирование | `/api/administration/...` |
| Публичные данные сайта и меню | `GET /api/site`, `GET /api/menu` |
| Поиск | `GET /api/search?q=...` |
| Публичные формы | `GET /api/forms/{code}`, `POST /api/forms/{code}/submit`, `GET /api/forms/{code}/results` |
| Корневой ресурс | `GET/HEAD /api/resources/resolve` |
| Ресурс или элемент библиотеки | `GET/HEAD /api/resources/resolve/{resource-path}` |
| Данные runtime | `GET /api/_cms/runtime` |

Публичные API выбирают сайт по домену запроса и соблюдают его права доступа.
Отсутствие обязательного входа в админку не делает закрытый сайт или ресурс
публичным. Управляющие API сохраняют обязательную аутентификацию и свои проверки
прав независимо от публичных маршрутов.

## Ошибки HTTP 5xx в журнале

Каждый ответ API со статусом `5xx` записывается в access log на уровне `ERROR`
и содержит атрибут `error.message`. В запись также входят HTTP-метод, маршрут и
ID запроса. Если обработчик располагает исходной причиной ошибки, он добавляет
её сообщение в эту запись; текст API-ответа при этом остаётся безопасным и не
раскрывает внутреннюю причину. Если причина не передана, `error.message`
содержит стандартное описание HTTP-статуса. Значение, вызвавшее panic,
редактируется и не попадает в журнал.

Для диагностики сбоя создания сайта или другой операции сопоставьте ответ с
записью по ID запроса и проверьте серверный журнал. Формат и место хранения
журнала определяются настроенным приложением логгером; см.
[запуск и конфигурацию](startup.md#изменение-композиции).

## Путь страницы и адрес API

Контракт окончательного удаления файлового поля и состояния `pending` описан в
[документации Core](modules/core/file-field-deletion.md).

### Media-поля в публичных ответах

В публичных ответах сайта значение объявленного поля типа `media` передаётся
объектом `{id, url, mime_type, size, settings}`; для множественного поля —
массивом таких объектов, а внутри `repeater` это правило применяется рекурсивно.
`settings` содержит заполненные метаданные из схемы, выбранной настройкой поля.
Если Media или файл отсутствует либо недоступен на публичном диске, значение
равно `null`; в массиве соответствующая позиция сохраняется. Для локального
хранилища `url` — относительный адрес, например `/_cms/files/{fileID}`. Path и
query, настроенные в `BaseURL` локального диска, сохраняются в адресе. Для
S3-хранилища с настроенным публичным адресом, включая CDN, это абсолютный URL,
сформированный из адреса хранилища.

Этот формат используется в публичных полях настроек сайта, template-полях ресурса
и полях публичных виджетов, включая выборки ресурсов и библиотек. Числовое
`image_media_id` у элемента списка ресурсов — отдельное стандартное свойство и
сохраняет ID. Управляющие API для чтения и записи полей сохраняют ID Media.
Формат и пример объекта приведены в разделе [контекста Core-виджетов](modules/core/widgets.md#контекст-пользовательских-виджетов).
Абсолютная ссылка направляет браузер на S3/CDN-хост, поэтому передача файла может
обслуживаться внешней инфраструктурой; реальная задержка зависит от её настройки
и сети.

Путь ресурса `/about` хранится как `/about`. Для получения JSON клиент
запрашивает `GET /api/resources/resolve/about`; корневой ресурс сайта доступен
через `GET /api/resources/resolve`. Путь `/api/resources/resolve/` с завершающим
слешем не является корневым маршрутом и возвращает 404. Для ресурса
`/news/article` используйте `GET /api/resources/resolve/news/article`. Те же
адреса принимают `HEAD`; ответ
не содержит тела. Прочие методы на resolver возвращают `405 Method Not Allowed`
и заголовок `Allow: GET, HEAD`.

Пути ресурсов в ответах, ссылки меню, поисковой выдачи и SEO остаются адресами
страниц сайта: например, `/news/article` на сайте остаётся
`https://example.com/news/article`. Это относится и к LibraryItem. Внутреннее
HTTP-перенаправление типа ResourceLink ведёт на resolver API: для корня сайта —
`/api/resources/resolve`, для целевого пути `/news/article` —
`/api/resources/resolve/news/article`. Тип Link сохраняет заданный внешний URL.

### Хлебные крошки ресурса

Успешный JSON-ответ страницы, библиотеки или элемента библиотеки включает
`resource.breadcrumbs` — массив объектов
`{title, link}`. В нём идут видимые опубликованные предки от корня к текущему
ресурсу; для текущего ресурса `title` берётся из `menu_title`, а если он пуст,
из `title`. `link` — публичный путь страницы без `/api/resources/resolve`.
Пустой результат передаётся как `[]`. Неопубликованные, снятые с публикации и
удалённые ресурсы пропускаются; `in_menu: false` сам по себе не исключает ресурс
из цепочки.

Например, при дереве `Главная → Новости → Главные новости → Главная новость`
крошки последней страницы содержат эту последовательность. Для отдельной
главной-ресурса и дерева `Новости → Главные новости → Главная новость` результат
с `IncludeHomeInBreadcrumbs: false` начинается с «Новости», а с `true` — с
«Главная». Для дерева `Главная → События → Событие 1` результат при обоих
значениях начинается с «Главная»: корень уже является предком, поэтому повторно
он не добавляется.

Например, для текущей страницы «Главные новости» ответ содержит:

```json
{
  "resource": {
    "breadcrumbs": [
      {"title": "Главная", "link": "/"},
      {"title": "Новости", "link": "/news"},
      {"title": "Главные новости", "link": "/news/main"}
    ]
  }
}
```

Метаданные цепочки кэшируются в кэше репозитория Core. Статус публикации
проверяется при каждом запросе, поэтому запланированная публикация и снятие с
публикации учитываются без ожидания истечения кэша.
Включение корневой страницы настраивается через
`Profile.Settings.IncludeHomeInBreadcrumbs`; описание настройки и примеры — в
[документации профилей](profiles.md#хлебные-крошки).

Для страницы LibraryItem хлебные крошки описывают маршрут публичного URL: в
цепочку входят предки ресурса-библиотеки и сама страница элемента. Для зеркала
используется публичный путь зеркала и элемента на текущем сайте.

Старые URL ресурсов, например `/api`, `/api/`, `/api/about` и
`/api/news/article`, возвращают 404; другие нераспознанные маршруты также
возвращают обычный 404. Зарегистрированные API, например `/api/site` и
`/api/menu`, продолжают работать. Прежние API-адреса
`/site`, `/menu`, `/search`, `/forms/...`, `/_cms/runtime` и выдача ресурсов вне
`/api` не обслуживаются: backend возвращает 404 без алиасов и перенаправлений.
`/api/api/...` также не обслуживается.

Исключения: доставка файлов по `/_cms/files/...` (включая подписанные ссылки)
и проверка запуска `/healthz` сохраняют свои адреса. Базовые URL файловых дисков
и `ADMIN_API_TARGET` указывают на origin backend без добавления `/api`.

## Регистрация маршрутов модулей

`httptransport.Registrar` принимает пути относительно `/api`: например,
`Pattern: "/search"` публикуется как `/api/search`. `Group` и `Mount` используют
ту же базу. Сервер снимает внешний префикс ровно один раз перед вызовом
публичного обработчика; `request.URL.Path` внутри него содержит относительный
к API путь. Префикс для генерируемых API-ссылок задан константой
`httptransport.APIPrefix`.

API-пространства `/auth`, `/admin`, `/sites`, `/site-profiles`, `/files`, `/media`,
`/administration`, `/_cms` и `/api` зарезервированы относительно общего префикса.
Модуль не может зарегистрировать в них литеральный маршрут или mount.
Запросы внутри этих пространств не передаются публичным ресурсам, включая
неизвестные адреса административных операций.

Site-management contributions сохраняют базу `/api/sites/{siteID}/{module}`.
Их handler объявляет только оставшийся относительный путь; например, Mail
объявляет `/send`, а внешний запрос идёт на `/api/sites/{siteID}/mail/send`.

## Динамические зоны виджетов

Публичный ответ ресурса содержит `widgets` как объект `код зоны → массив виджетов`.
Коды определяются шаблоном; названия и размеры контейнеров в ответ не включаются:

```json
{"widgets":{"main":[],"aside":[],"footer":[]}}
```

Объявленные зоны присутствуют даже пустыми. Если зон нет, используется
`{"widgets":{"default":[]}}`. При наличии зон дополнительный `default` включается
только при наличии собственных виджетов или виджетов исчезнувших зон. Выключенные
виджеты сохраняют контейнер, но не рендерятся. Без выбранного шаблона `widgets` — `{}`.
Порядок ключей JSON не задаёт разметку страницы.

Management metadata `widget_areas` — упорядоченный массив зон с полями
`code`, `label`, `admin_span`, `supports_resource_widgets` и `items`. `items`
передаёт скомпилированный порядок `{kind: "widget", code}` для статических
виджетов шаблона и `{kind: "resource_widgets"}` для слота редактируемых
виджетов ресурса. Конфигурация статических виджетов не включена; админка
показывает название и описание по общим определениям виджетов. Если шаблон не
объявляет зоны, `widget_areas` описывает `default` с неявным слотом. Полный
пример и поведение редактора описаны в [зонах виджетов](widget-areas.md).

`area` в сохранённой привязке остаётся исходным кодом. Админка помещает
привязки отсутствующих редактируемых зон в `default`; только явный перенос
меняет их код. Полная перестановка передаёт неизменённые коды остальных
привязок и текущий `expected_version`.

## Зеркала библиотек

`library_mirror` позволяет получать ресурс чужой библиотеки на текущем Host:
`GET /api/resources/resolve/{mirror-path}/{item-pattern}`. Например, элемент
`annual-report` зеркала `/press` получают запросом
`GET /api/resources/resolve/press/annual-report`. Ответ содержит исходный ID и
локальный `resource.path`, шаблон/виджеты/SEO берутся из профиля источника.
`canonical` сохраняет исходное значение. Корневая страница зеркала имеет свои
данные и шаблон; её JSON получают через
`GET /api/resources/resolve/press`. Списки и независимые query-курсоры описаны в
[Core: виджеты](modules/core/widgets.md).
